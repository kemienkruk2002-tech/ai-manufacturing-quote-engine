### P2 — SQL completeness CHECK accepts partial identity and permits uniqueness bypass

Location: `services/api/Persistence/Migrations/012_rfq_extraction_idempotency.sql:10-14`, with index at `:17-19`.

The second OR branch lacks explicit NOT NULL checks. For `(version=NULL, key='retry-1', hash=64 valid lowercase hex)` the CHECK evaluates NULL, which PostgreSQL accepts. The NULL version also allows repeated identical tenant/RFQ/key combinations through the default unique index. Other partial tuples (including non-NULL version/key with NULL hash) also pass. A read-only PostgreSQL SELECT of the exact expression returned `incomplete_identity_check_is_null = true`; no database writes were made for this audit. PostgreSQL 16 documents both CHECK acceptance of NULL and default unique NULL semantics: https://www.postgresql.org/docs/16/ddl-constraints.html.

Require either all three identity fields NULL (legacy rows) or all three explicitly NOT NULL plus current format checks. Add direct PostgreSQL tests covering all six partially NULL permutations and duplicate complete tuples. Preserve already-applied migration checksums: use a new migration unless non-application of 012 is positively established and repository change policy permits editing it.

### Additional P2 schema hardening — New audit pointer does not enforce tenant scope

Location: `services/api/Persistence/Migrations/012_rfq_extraction_idempotency.sql:5`.

`audit_event_id REFERENCES audit_events(id)` accepts a referenced audit from any tenant; the surrounding attempt/RFQ FKs do not constrain the referenced audit tenant. Existing `audit_events` already has `UNIQUE(tenant_id,id)` (`004_audit.sql:13`), so a composite `(tenant_id,audit_event_id)` FK can enforce this boundary. The column is currently unused by production inserts, so this audit has **not** established an exposed cross-tenant read or active leak. Address the schema invariant before using this pointer for replay. Verify audit entity/RFQ/action consistency within the atomic repository write as well.
